Health data pipeline

How a heartbeat on the watch and a step on the scale become facets in Anam, which machine does each part, and how to tell when a part has stopped.

State as of 30 September 2026. Stages one to four were checked on 29 September, and stage five on 30 September.

where the data starts a process that runs a SQLite file Anam

The five stages

  1. Collect from Garmin The garmindb container on unraid runs its own cron. It downloads from Garmin Connect, imports, then analyses. The analyse step writes garmin_summary.db, which holds one row per day with Garmin's own min and max. Nothing in ductile runs this container.
  2. Collect from Withings The withings plugin in the unraid ductile gateway polls every six hours and writes withings.db. It raises one event per new weigh-in.
  3. Notice that something changed The garmin plugin checks the modification time of garmin.db every 30 minutes. When it moves, the plugin raises health.new_data with the days that changed. Withings needs no watcher, because its plugin raises withings.measurement_recorded itself.
  4. Summarise Either event starts the health ETL. Ductile runs it as a one-shot container from the ductile-healthdata image. It reads both raw stores and writes day, week, month and year rows to healthdata.db.
  5. Ingest into Anam The ThinkPad ductile gateway runs anam ingest every hour. It reads healthdata.db over the Projects share. It also reads withings.db and the blood pressure export directly. Every row passes the gate and lands in ledger.db.
Stage five runs on a clock, not on an event. The ingest takes about two seconds and an unchanged row is a no-op, so an hourly run costs nothing when there is no news. New data reaches Anam within an hour of the ETL writing it.

What a day looks like

The ETL writes one row per metric per period. Each row has a value, and a min and a max where Garmin supplies them. Anam groups the rows for one period into six facets, one per metric group. This is 27 September 2026.

Body battery has a range and no single value, because Garmin reports it that way. Steps are a count, so they have no range. A day's sleep has one night in it, so its min and max equal its value. For a month they differ.

What does not

  • Garmin samples. About 2.7 million minute-level rows for heart rate, stress, respiration and blood oxygen. Daily summaries were chosen instead.
  • Garmin activities. 198 activities and their track records. No worker reads them.
  • Garmin weeks after 2024. GarminDB counts weeks in seven-day blocks from 1 January. The ETL looks them up by Monday, so they match only in a year that starts on a Monday.
  • Nights with no recording. GarminDB writes zero minutes when the watch recorded no sleep. The ETL writes no sleep row for that period, so Anam does not claim a sleepless night.

How to tell a stage has stopped

Every stage can stop without any error. The process stays up and the gateway stays healthy. The only reliable sign is that its output stops moving. Check the newest date each stage holds.

Since 30 September the ThinkPad gateway does this once a day, as job health_staleness, by running scripts/pipeline-staleness.sh from the Anam repository. It compares each stage with the one before it. When a stage is more than two days behind, a message from Anam names it. When a stage cannot be read, the job fails and Ductile Ops says so. When all is well, nothing is sent. To run it by hand:

~/Projects/anam/scripts/pipeline-staleness.sh

The queries it runs:

# 1. Garmin collected: newest day in GarminDB
sqlite3 "file:/mnt/Projects/healthdata/garmin/DBs/garmin_summary.db?mode=ro" \
  "SELECT MAX(day) FROM days_summary"

# 2. Withings collected: newest measurement
sqlite3 "file:/mnt/Projects/healthdata/withings/withings.db?mode=ro" \
  "SELECT MAX(date) FROM measurements"

# 3 and 4. ETL ran: newest summarised day, and when each source last ran
sqlite3 "file:/mnt/Projects/healthdata/healthdata.db?mode=ro" \
  "SELECT MAX(period_start) FROM summaries WHERE period_type='day';
   SELECT source, last_sync FROM sync_status"

# 5. Anam ingested: newest fact-time per type
sqlite3 "file:$HOME/.local/share/anam/ledger.db?mode=ro" \
  "SELECT type, MAX(fact_time) FROM facet GROUP BY type"

A healthy pipeline has the first three within a day of each other. The ETL's run history is in the unraid gateway:

/mnt/Projects/unraid_admin/unraid_cmd.sh \
  'docker exec ductile /app/ductile job logs --plugin health_data_summary --limit 5 \
   --config /app/config/config.yaml'

How Anam stays up to date

The ThinkPad gateway has a scheduled job, anam_ingest, declared in /etc/ductile/anam.plugins.yaml. It runs the installed binary as matt.

/usr/bin/timeout -k 10 300 /home/matt/go/bin/anam ingest
What happenedWhat you see in Discord
New or revised rows were admittedA message from Anam with the count per source
Nothing was newNothing
The run failedA message from Ductile Ops naming anam_ingest and the error

An ingest reads every source before it admits anything. If the Projects share is not mounted, the run fails at the first source it cannot read and the ledger is not opened for writing.

The job runs the binary in ~/go/bin, not the one in the repository. After a change to Anam, install it:

cd ~/Projects/anam
make install

To run an ingest by hand:

ANAM_PERSON_ID=matt ~/go/bin/anam ingest

An ingest is safe to repeat. Rows that have not changed are skipped. A row whose summary moved is written as a new version, and the old one is kept.

Its run history is in the ThinkPad gateway:

sudo -u ductile ductile job logs --plugin anam_ingest --limit 5 \
  --config /etc/ductile/config.yaml

Why it had stopped

On 28 September 2026 Anam's Garmin data ended at 16 July. The ETL had been moved twice and neither move was finished.

GenerationWhereWhat happened
Senechalunraid, hourly cronKept running on Garmin files that stopped changing on 22 March. Switched off 29 September.
ThinkPad gatewayThinkPadThe working stopgap from March. Its ETL step was dropped in July when the gateway moved to the privileged setup.
Unraid gatewayunraidRegistered in April and never ran. It had no trigger for either source, and its image was not on the server. Live since 29 September.
Nothing alerted at any point. A pipeline that nothing triggers leaves an empty job log, and an empty log reads the same as a quiet day.

Still open

  • A gateway job can stall without failing. On 27 September the ThinkPad gateway could not record that a job had finished, because its state database was locked. The job stayed marked as running and the scheduler skipped it 6,840 times over three days. That is not a failure, so nothing is sent. A restart clears it. The daily staleness check is what catches it, a day late.
  • A real Withings weigh-in has not yet passed through the new trigger. A synthetic event did.
  • Day boundaries are UTC. Garmin's day is a local calendar day. Anam reads its start as midnight UTC, about ten hours early for Sydney.
