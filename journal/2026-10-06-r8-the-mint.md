# R8: the mint, and the test that is the value

`anam checkpoint` exists. It folds the ledger at the head, splits the live value by monthly bucket,
and writes a new version of every bucket whose value differs from its last checkpoint. The decision
behind it is in [[checkpoint-is-a-replay-floor]], written three months before the code and already
right: staleness is dedup'd by hash, not tracked.

## What was on the table

The card's criteria were written on 2026-09-29. The last one was the trap: a source that revises a
measurement's date carries the same facet into another bucket, and a union of stale bucket values
would count it twice. The architecture names `W > Wᵥ` as the re-mint test, and the first design for
this session took that literally. Since `W` is global, telling *which* bucket an event touched needs
the event's bucket, which the event index does not hold, so the plan was to add `bucket_id` to
`anam_event_index` at catch-up, bump the derived schema, and rebuild `tracking.db`.

## Hickey × Armstrong, before code

Hickey's question was where the state lives. The proposed design kept a second account of change
(per-event bucket ids) to predict whether a value had moved, when the value itself can be built and
asked. The bucket's hash at `W` compared with its head checkpoint's is exact: equal means nothing a
reader could see has changed. `W > Wᵥ` is only sufficient, and on its own would re-mint every bucket
on every ingest. The hash also covers the moved-fact-time case for free, because both buckets'
hashes move. The second index was bookkeeping about the value, complected with it; drop it. No
schema bump, no rebuild. `W > Wᵥ` stays in the architecture as the pre-filter an incremental mint
would add in front of the fold.

Armstrong's question was what crashes. The value file is written before its row, and both are
idempotent, so a crash between them leaves a correctly named orphan that the re-run writes again
(a no-op) and then references. A crash between buckets leaves the earlier ones minted. Two mints
racing to the same version collide on the `(span_id, v)` primary key, and the loser is told to
re-run. The ledger is opened read-only; a checkpoint is not something Anam learned. The checkpoint
rows are pinned to the ledger's id, like every other derived row.

One case fell out of writing the union: a bucket whose last facet is retracted is no longer in the
fold, so the mint finds it through its head and re-mints it as the empty value. Otherwise a
composed read would still list the facet.

## What was built

- `internal/mint` — `Run` (mint at the head, `--dry-run` on the same path), `Partition` (entries
  by bucket, arithmetic on fact-time), `Compose` (union of bucket values; byte-identical to a fold
  of the same facets, because `NewValue` imposes the one order), `Load` (a value back from the
  artifact tier, refused if its bytes are not the value the row names).
- `internal/store/ops/checkpoint.go` — `SpanHeads`, `Checkpoints`, `AppendCheckpoint` over the
  table and view that have sat empty since R2.
- `anam checkpoint` and `anam checkpoint list`.
- Every acceptance criterion on the card is a test over a real ledger, a real operational store
  and a real artifact directory, including the moved-fact-time case with a Withings-shaped
  definition whose identity is an id and whose date is a separate field.

## Numbers

Live dry run at `W=11381`: 34 monthly buckets over 11,246 live facets, mean 330, worst 744
(`bucket:2025-03`), thinnest 19, 0.8 s wall for the whole fold and partition. The architecture's
"worst bucket prices a re-mint" was 575 when written and is 744 now.

## Not built, on purpose

The read path still folds. `timeline` does not yet start from a checkpoint and replay since
`covers_w`; `Compose` and `Load` are the pieces, and the equality test between a composed read and
a full fold is what makes wiring them in safe. The adaptive trigger is still deferred, and the
first real mint is a command Matt runs.
